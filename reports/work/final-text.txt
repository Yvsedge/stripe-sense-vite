1. Introduction 
1.1 Background 
Urine reagent strips use colour changes on multiple pads to support screening. A 
photographed strip can be compared with a reference chart, but the image and its patient 
details must also be recorded consistently. A web application provides a convenient way to 
collect an image, review colour matches and revisit earlier results. 
 
StripeSense was developed as a Full Stack Development mini project. The main academic 
objective is to integrate React, Express, Node.js and MongoDB through a usable application. 
Its implemented image pipeline uses reference-colour comparison rather than a trained 
machine-learning model. The current outputs are unvalidated estimates and do not diagnose a 
medical condition. 
1.2 Problem Statement 
Individuals and doctors need an organised way to associate strip images and colour-matching 
results with the correct person. Keeping photos and notes separately makes retrieval difficult 
and creates the risk of mixing records. The project addresses this software workflow through 
account-based patient records, authenticated uploads and searchable saved reports. It does not 
address clinical validation or replace a laboratory analyser. 
1.3 Proposed Solution 
The application provides a public landing page and a private workspace. A user registers as a 
doctor or individual, signs in, adds a patient, uploads a horizontal ten-pad photo and a 
reference JSON profile, selects the pad row and submits the analysis. Express validates the 
request, runs the colour comparison and stores the result with its source image in MongoDB. 
React retrieves the report through Axios for review, history filtering and printing. 
1.4 Objectives and Scope 
• Provide registration, sign in, persistent sessions and sign out. 
• Create patient records and associate each test with its patient and account owner. 
• Process a ten-pad image using a supplied colour-reference profile. 
• Save and retrieve reports, source images and analysis metadata in MongoDB. 
• Demonstrate API integration, input validation, account isolation and automated testing. 
Scope includes a desktop-first interface, light and dark themes, patient creation, reference 
matching, history, report printing and test deletion. Hardware capture, trained ML, verified 
concentration estimation, medical diagnosis, shared clinical teams and public cloud 
deployment are outside the implemented scope. Patient/test editing is a future enhancement.

3. SYSTEM DESIGN 
3.1 System Architecture 
 
Axios requests reach Express through the Vite proxy. The backend validates ownership, calls 
the analyser and persists the result. Responses follow the same API path back to React. 
Figure 1  System architecture

4. APPLICATION DESIGN AND IMPLEMENTATION 
4.1 User Interface and Navigation 
 
Figure 4  Public landing page 
The public landing page explains the implemented workflow and links to sign in. The 
authenticated workspace provides Dashboard, Analyse photo, Test history and Patients 
navigation. Sign in includes registration and account-type selection. Light/dark mode is 
available on public and private screens and is remembered in localStorage. 
 
The dashboard displays saved record counts and recent tests rather than illustrative graphs. 
Analysis includes patient selection, profile/image upload and a crop overlay. Reports show 
colour categories, measured/reference RGB, Delta E and review flags. The layout prioritises 
desktop use; the private workspace has a minimum width and is not presented as fully 
mobile-optimised.

4.2 Frontend Implementation 
 
Figure 5  Sign in screen 
React functional components use useState, useEffect and useRef for forms, asynchronous 
records and image selection. React Router separates public pages from private routes. 
AuthProvider retrieves the current session; RequireAuth redirects signed-out users and 
displays connection errors without exposing protected pages. 
 
A shared Axios client uses /api with a request timeout. FormData carries the photo, patientId, 
profile and crop. The image preview uses object URLs and releases them when replaced. 
ThemeProvider persists the selected appearance. Components for reports and interpretation 
keep detailed colour measurements separate from the user-facing explanation. 
4.3 Backend and API Implementation 
Express applies a JSON size limit, route-scoped Multer upload handling and central error 
responses. Multer accepts JPEG, PNG or WebP metadata with an 8 MB file limit; Sharp 
performs actual decoding and limits the decoded pixel count. A normalized image above 10 
MB is rejected before persistence. 
 
Passwords are salted and hashed with scrypt. Login issues a random session token in an 
HttpOnly, SameSite=Strict cookie; only its SHA-256 hash is stored in MongoDB. Logout 
deletes the session. Origin checks and in-process attempt limits provide additional protection. 
Production cookies require HTTPS; deployment hardening remains necessary before real-
world use.

The MongoDB driver performs insertOne, find, findOne and deleteOne operations. Patient 
creation stores the account owner and generates a patient code when omitted. Uploading a 
test verifies that the selected patient belongs to the signed-in account, then inserts a complete 
analysis record. List queries omit binary images; a separate authenticated endpoint serves the 
saved PNG. 
 
Read operations support patient-filtered test history, individual reports and source-image 
retrieval. Deleting a test removes its embedded source image with the record. Patient and test 
editing are not implemented. Session creation/deletion belongs to authentication and is not a 
substitute for a record-editing feature. 
4.5 Validation and Error Handling 
Missing patient names and unsupported uploads are rejected with actionable errors. Duplicate 
patient codes within an account return 409. Malformed profiles, invalid crop rectangles and 
image decode failures return an analysis validation error rather than storing a partial test. 
 
Unknown or other-account report IDs return 404, including image and deletion endpoints. 
Network failures produce a connection message in the frontend. Near-tied colour matches are 
flagged for review and are not forced into a known estimate category.

5. TESTING AND RESULTS 
5.1 Testing Approach 
The Node.js test runner executes analyser and interpretation unit tests plus a real 
Express/MongoDB integration test. The integration test uses an ephemeral HTTP port and a 
uniquely named temporary database, which it removes after execution. 
 
On 30 October 2026, all eight tests passed with TEST_MONGODB_URI set to local 
MongoDB. The frontend production build passed. Browser checks covered navigation, 
protected-route redirects and theme persistence. Postman was not used for these recorded 
tests.

8. CONCLUSION AND FUTURE SCOPE 
8.1 Conclusion 
StripeSense brings account-based patient records, reference-colour matching and saved 
reporting into one MERN application. React provides the interface, Axios connects it to 
Express, and MongoDB persists users, sessions, patients and tests. Automated checks 
confirm the implemented software behavior, including ownership isolation and retrieval of 
saved results. 
 
The project demonstrates full-stack integration without claiming clinical measurement 
accuracy. Its colour outputs are estimates from a supplied reference profile. Further work is 
required for complete record editing, public deployment, manufacturer calibration and any 
validated medical interpretation. 
8.2 Future Scope 
Future work includes patient/test editing with audit history; password reset and email 
verification; pagination beyond the current 500-record lists; broader mobile workspace 
support; private object storage for larger images; and secure public deployment. 
Manufacturer-specific reference profiles, varied-layout pad detection and evaluation against 
labelled real-strip images would be required before extending analysis beyond the current 
controlled scope. Shared-care access would need explicit consent and fine-grained 
permissions.
